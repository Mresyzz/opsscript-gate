## 本轮新发现的问题与修复记录

### 1. `discovery.py` 中 `_is_ignored_path` 误将前导 `./` 路径判定为忽略项
* **文件位置**：`src/opsscript_gate/discovery.py`
* **问题成因**：
  `_is_ignored_path` 将路径按 `/` 切分后遍历每个 `part`，直接使用 `part.startswith(".")`。当路径是以 `./` 开头（例如 `./scripts/install.sh` 或 `./run.sh`）时，首个 `part` 为单个点 `.`，`'.'.startswith(".")` 恒为 `True`，导致合法脚本被错误判定为忽略项。
* **修复方案**：
  在切分前先剥离前导 `./`，并将 `part in (".", "..")` 显式排除在隐藏目录判断之外。
* **测试用例**：
  新增 `tests/test_runner.py::test_is_ignored_path_dot_slash_and_hidden`。

### 2. `runner.py` 中 `_is_wait_timeout_error` 无法识别嵌套异常原因链
* **文件位置**：`src/opsscript_gate/runner.py`
* **问题成因**：
  Docker SDK (urllib3 / requests) 发生超时异常时，常将底层的 `ReadTimeout` 或 `SocketTimeout` 包装在 `requests.exceptions.ConnectionError` 或顶层异常中。原函数只检查了外层异常类名，导致被包装的真实超时被误报为通信崩溃（`DistroStatus.ERROR`），且未能触发超时强杀逻辑。
* **修复方案**：
  在 `_is_wait_timeout_error` 中遍历 `__cause__` 与 `__context__` 异常链，全面识别深层超时错误。
* **测试用例**：
  新增 `tests/test_runner.py::test_is_wait_timeout_error_cause_chain`。

---

### 3. `cli.py` 中 `--output` 指定已有目录时缺乏前置拦截
* **文件位置**：`src/opsscript_gate/cli.py`
* **问题成因**：
  若用户误将已存在的目录传给 `--output`（例如 `--output reports/` 或 `--output .`），原逻辑在跑完所有耗时的容器矩阵测试后，才在 `publish_output` 中因 `write_text` 抛出 `IsADirectoryError` 或 `PermissionError`，严重浪费时间。
* **修复方案**：
  在执行矩阵前增加 `if output_path.is_dir(): sys.stderr.write("Error: output must name a file, not an existing directory\n"); return 1` 提前拦截。
* **测试用例**：
  新增 `tests/test_runner.py::test_cli_output_rejects_existing_directory_early`。

---

### 4. `remediation.py` 扩充跨发行版包管理器互踩诊断规则
* **文件位置**：`src/opsscript_gate/remediation.py`
* **问题成因**：
  此前仅包含 Debian/Ubuntu（apt）与 Alpine（apk）的双向匹配。当脚本在 Debian/Ubuntu/Alpine 上尝试调用 `yum` 或 `dnf`，或者在 Fedora/CentOS/RHEL 系列镜像上调用 `apt`/`apk` 时，系统只能报通用缺失错误，缺乏精准指引。
* **修复方案**：
  新增 `_match_debian_ubuntu_yum`、`_match_alpine_yum`、`_match_rhel_fedora_apt` 匹配器及专属修复建议。
* **测试用例**：
  新增 `tests/test_runner.py::test_remediation_enterprise_distro_package_rules`。

---

### 5. `runner.py` 中保护 `container.reload()` 避免网络抖动覆盖已取得的状态码
* **文件位置**：`src/opsscript_gate/runner.py`
* **问题成因**：
  在容器执行完毕后，`container.wait()` 已返回了包含 `StatusCode` 的字典，但随后的 `container.reload()` 调用缺乏异常防护。一旦容器刚好在退出瞬间发生通信抖动，会导致原本已成功完成的测试异常崩溃。
* **修复方案**：
  为 `container.reload()` 增加 `try-except` 防护，优先并安全地使用已拿到的有效退出码。

---

### 6. `remediation.py` 中 `curl`/`wget` 绝对路径匹配与最小容器缺失 `sudo` 修复规则
* **文件位置**：`src/opsscript_gate/remediation.py`
* **问题成因**：
  1. `_match_curl` 与 `_match_wget` 仅检查了命令名完全等于 `curl` / `wget`，当脚本使用 `/usr/bin/curl`、`/bin/curl` 等绝对路径调用时，无法匹配到建议规则。
  2. 最小化 Linux 容器镜像（Debian slim、Ubuntu、Alpine 等）默认不带 `sudo`，且容器通常本身即为 root 权限。当运维脚本带有 `sudo` 时会报 `sudo: not found`，此前缺乏专属修复建议。
* **修复方案**：
  提取命令路径中的 basename 统一进行匹配，并新增 `_match_sudo` 规则与针对性修复建议。
* **测试用例**：
  新增 `tests/test_runner.py::test_remediation_curl_wget_path_and_sudo`。

---

### 7. `reporter.py` 中 `_sarif_path` 与 `format_github_annotations` 非前导路径穿越漏洞
* **文件位置**：`src/opsscript_gate/reporter.py`
* **问题成因**：
  原代码仅使用 `startswith("../")` 检测路径逃逸，当相对路径为 `subdir/../../outside.sh` 时无法识别，导致逃逸路径被直接写入 SARIF 的 `artifactLocation.uri` 与 GitHub Actions `::error file=...`。
* **修复方案**：
  引入 `os.path.normpath` 彻底归一化，凡逃逸出工作区根目录者统一安全回退至 `os.path.basename`。
* **测试用例**：
  新增 `tests/test_runner.py::test_sarif_and_annotations_path_traversal_hardened`。

### 8. `cli.py` 中 `--output` 缺乏对 `.git` 目录与工程核心文件的防覆写防护
* **文件位置**：`src/opsscript_gate/cli.py`
* **问题成因**：
  原逻辑仅保护了脚本自身与配置文件，若用户指定 `--output pyproject.toml` 或 `--output .git/config`，会导致工程配置与版本库元数据被截断覆盖。
* **修复方案**：
  严禁向 `.git` 内部路径写入，并定义 `CRITICAL_PROJECT_FILES`（包含 `pyproject.toml`、`action.yml` 等）加入严格保护列表。
* **测试用例**：
  新增 `tests/test_runner.py::test_cli_output_protects_git_and_critical_files`。

### 9. `runner.py` 中 Docker 容器 OOM-Killed 强杀状态识别
* **文件位置**：`src/opsscript_gate/runner.py`
* **问题成因**：
  容器超出 `mem_limit` 时被 Linux 内核 OOM Killer 强杀（退出码 137），原代码仅笼统报非零退出码，丢失了内存超限关键诊断信息。
* **修复方案**：
  读取容器 `State.OOMKilled` 标识，当为 True 时明确标注 `Container exceeded memory limit ({mem_limit}) and was killed by OOM killer`。
* **测试用例**：
  新增 `tests/test_runner.py::test_runner_oom_killed_detection`。
